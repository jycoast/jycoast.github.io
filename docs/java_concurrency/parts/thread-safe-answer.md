---
title: 产生线程安全问题的根源是什么？
---

上一节留了个问题：把 `count` 声明成 `volatile`，那个计数器就能得到 2000 了吗？

答案是不能。但这个「不能」比「能」更值得琢磨——它说明那三种失效背后，是**三套完全不同的机制**，而 `volatile` 只对付得了其中一套。

把它们对上号，问题的根源就清楚了。

### 三个现象，三个元凶

| 你看到的现象 | 被破坏的特性 | 真正的元凶 |
| --- | --- | --- |
| 线程 A 改了变量，线程 B 像没看见 | 可见性 | CPU 缓存 |
| 两个线程各加一次，结果只加了一次 | 原子性 | 线程切换 |
| 代码写着先 A 后 B，实际先执行了 B | 有序性 | 指令重排 |

这三件事分别发生在三个层次：缓存是硬件，线程切换是操作系统，指令重排是编译器与处理器。它们是同一台计算机为了快而付出的三笔代价——理解了每一笔代价怎么来的，也就理解了每一种 bug 为什么长得不一样。

### 可见性：缓存带来的

先说一个比计数器更直观的现象。

线程 A 负责把 `flag` 置为 `true`，线程 B 负责等它：

```java
// 线程 A
flag = true;

// 线程 B
while (!flag) {
    // 等 A 通知，什么也不做
}
```

按直觉，A 一写完，B 就该跳出循环。可现实里 B 很可能**一直转下去**，转到你不得不 `kill` 掉进程。

原因在于：单核时代，所有线程共用同一个 CPU 缓存，A 写进缓存的值，B 一定读得到。到了多核时代，每个核心有了自己的缓存，`flag` 在两个核心里各存了一份。A 的修改落在了 CPU-1 的缓存里，而 B 一直在 CPU-2 的缓存里读那个从没变过的 `false`。

<div class="note info"><p>「线程 A 写、线程 B 读」这类程序，问题往往不在写错了，而在<b>读的根本不是同一份数据</b>。这是多核给软件开发者留下的一个隐形的坑——代码里明明只有一个 <code>flag</code> 变量。</p></div>

**一个线程对共享变量的修改，另一个线程能够立刻看到，我们把这种特性称为可见性。**

缓存的完整故事（MESI 协议、伪共享、写缓冲与失效队列）在 CPU 缓存那一篇里展开，这里只需要记住一件事：**只要数据有副本，就有「谁的那份是最新的」这个问题。**

### 原子性：线程切换带来的

第二笔代价来自操作系统。

早期的 CPU 实在太贵，人们想让它同时服务多个程序，于是发明了多进程：操作系统给每个进程分一小段时间——比如 50 毫秒，时间一到就换下一个。这 50 毫秒叫**时间片**，换下一个进程的动作叫**任务切换**。

切换本身是为了效率。问题在于切换的粒度：**它可以发生在任意一条 CPU 指令执行完之后，而不是任意一条 Java 语句之后。**

这两者的差别，就是上一节那个 `count++` 的死因：一条 Java 语句被拆成了三条指令，而切换恰好插在中间。上一节的交错表已经把它拆开看过，这里不再重复，只把结论拎出来：

**一个或多个操作在执行过程中不被中断的特性，我们称为原子性。**

<div class="note warning"><p>CPU 能保证的原子操作是<b>指令级</b>的，不是语句级的。这是整件事里最反直觉的地方：我们写 <code>count++</code> 时，脑子里它就是一个不可分割的动作，可机器眼里它有三步。</p></div>

### 有序性：指令重排带来的

第三笔代价更隐蔽——它甚至不需要别的线程插手，光是编译器自己就会改你的代码。

来看一个看起来万无一失的单例：

```java
public class Singleton {

    private static Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();   // 这一行有问题
                }
            }
        }
        return instance;
    }
}
```

双重检查加锁，教科书级别的写法。但它在多线程下是**错的**，问题就出在 `new` 那一行。

我们以为 `new` 是「分配内存 → 初始化对象 → 把地址赋给变量」一步到位，可经过重排之后，顺序可能变成：

```text
1. 分配内存 M
2. 把 M 的地址赋给 instance     ← 提前了
3. 在 M 上初始化对象
```

于是线程 A 执行到第 2 步就被切走，此时 `instance` 已经不为 `null`，但对象还没初始化完。线程 B 进来一看，第一个 `if` 直接通过，拿着一个「空壳对象」就去用了。

**程序按代码的先后顺序执行，我们把这种特性称为有序性。**

为什么要重排？因为 CPU 里有流水线：一条指令分成多个步骤，步骤之间可以并行推进，前一条还没算完，后一条就能开始准备。但流水线最怕停顿——比如算 `a = b + c` 时要等 b、c 装载完才能加，这段空等就是浪费。既然要等，不如顺手把后面那条 `d = e - f` 的 e、f 先加载进来。**重排是在填流水线的空档。**

重排有三种来源：

| 类型 | 谁在动 | 它凭什么敢动 |
| --- | --- | --- |
| 编译器优化重排 | 编译器 | 单线程语义不变 |
| 指令并行重排 | 处理器 | 指令之间没有数据依赖 |
| 内存系统重排 | 缓存与写缓冲 | load/store 的完成时机被打散 |

关键在于最后一列：**它们只保证单线程语义不变，从没承诺过多线程下也对。** 对编译器来说，你的单例代码里没有任何一行写错了，它只是在合法地优化。

（双重检查锁的完整分析和 `volatile` 为什么能救它，留在 JVM 那一篇讲。）

### 三者常常一起出现

分开讲是为了看清机制，但真实出问题时，三种特性往往同时在场。

还是那个单例：线程 B 拿到一个未初始化的对象，既是**有序性**问题（`new` 的三步被重排），也是**可见性**问题（线程 B 看到的 `instance != null` 是一个尚未发布完整的值）。而修好它，`volatile` 一次就把两件事都办了——它既禁止重排，也保证写立即对其他人可见。

所以别把三者当成三个独立的知识点去背。更实用的问法是：

| 特性 | 谁在破坏它 | 该往哪个方向治 |
| --- | --- | --- |
| 可见性 | 缓存副本 | 让写刷新、让读失效 |
| 原子性 | 切换打断 | 让一组操作不可分割 |
| 有序性 | 重排优化 | 在需要的地方插屏障 |

这三行，就是后面所有关键字和工具类的设计原点：`volatile`、`synchronized`、`Lock`、`Atomic` 这一大堆东西，没有一个能跳出这张表。

### 小结

到这里，问题的「靶子」算是立起来了：**并发 bug 不神秘，它只是三台机器为了跑得更快，各自在你背后做了点小动作。**
