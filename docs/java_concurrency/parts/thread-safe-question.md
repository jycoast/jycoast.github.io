---
title: 什么是线程安全问题？
---

你大概见过这样的 bug：本地怎么跑都对，上了生产就数据对不上；你想加一行日志看看，它偏偏又好了。

它不报错、不抛异常，日志里干干净净。你只能盯着一行「逻辑上绝不可能有问题」的代码，怀疑人生。

这类问题十有八九是同一个原因。要看清它，先从一个简单到不可能出错的例子看起。

### 从一个计数器开始

观察下面的程序，你觉得它会输出什么？

```java
public class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }

    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Runnable task = () -> {
            for (int i = 0; i < 1000; i++) {
                counter.increment();
            }
        };

        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start();
        t2.start();

        // 等待两个线程执行完
        t1.join();
        t2.join();

        System.out.println("最终计数: " + counter.getCount()); // 期待输出 2000
    }
}
```

两个线程各做 1000 次自增，除此以外没有任何复杂操作。凭直觉，结果应该是 2000。

但你把这段代码多跑几遍，会发现结果几乎每次都不一样——可能是 1873，可能是 1994，极少数情况下才刚好是 2000。

代码没错，逻辑也没错，可它给你的答案就是错的。

### 为什么 `count++` 会出错

答案藏在这行看起来「一步到位」的代码里。它不是一步，是三步：

```text
1. 读取 count 的当前值到寄存器   （read + load）
2. 寄存器里的值加 1              （计算）
3. 把结果写回 count              （assign + store）
```

既然有三步，就有「只做了一半就被打断」的可能。假设 count 当前是 5，两个线程这样交错执行：

```text
时刻  线程 A                    线程 B                  count
─────────────────────────────────────────────────────────────
T1    读取 count = 5                                     5
T2                              读取 count = 5           5
T3    计算 5 + 1 = 6                                     5
T4                              计算 5 + 1 = 6           5
T5    写回 count = 6                                     6
T6                              写回 count = 6           6   ← 丢了 1 次自增
```

两次自增，最终只加了 1。线程 A 和线程 B 都读到了 5，都写回了 6，其中一次的结果被覆盖掉了——这种失效方式叫**丢失更新**，是最容易被观察到的一种。

但还有更隐蔽的。

如果线程 A 改完 `count` 之后，**线程 B 读到的仍然是自己缓存里的旧值**，那么 B 接下来的一系列计算全都是基于过期数据做的：它可能一直在跟一个「不存在的 5」打交道，并且还会把这个错误的结论一路传下去。再极端一点，如果编译器认定循环里的 `count` 没有被别人动过，干脆把它提升到寄存器，整个 1000 次循环都不再访问内存——那线程 A 的修改对 B 来说就彻底消失了。

到这里，前面两种现象其实指向两个不同的原因：

- **原子性被破坏**：`count++` 的读-改-写三步被打断（就是上面那个丢失更新的例子）
- **可见性被破坏**：一个线程的修改，另一个线程看不到

而编译器和处理器为了优化性能，还会调整指令的执行顺序，带来第三个原因——**有序性**：代码实际执行的顺序，和你写的顺序可能不一样。

### 把这个问题定义清楚

回过头看那个计数器：它在单线程下完全正确，一到多线程就开始出错。**代码一个字没改，变的只是「谁在什么时候执行、执行到哪一步被打断」——结果依赖了时序，于是不再可控。**

所以线程安全问题可以这样定义：**一段在单线程下正确的代码，放到多线程环境下运行，产生了错误的结果。**（更严谨的说法引自《Java 并发编程实战》：当多个线程访问同一个对象时，如果不需要额外的同步与协调，调用它的行为仍然能得到正确结果，那这个对象才是线程安全的。）

<div class="note warning"><p>这里有个关键点最容易忽略：<b>它不一定错。</b>同样的代码、同样的线程数，这次是 1994，下次可能是 2000。所以它在测试环境往往复现不了，一路平安地过了压测，然后在上线当天以「数据对不上」的形式炸出来——而那时你手里只有一份对不上的数据，没有堆栈、没有日志，连是哪一行出的问题都要靠猜。这比一个必然报错的 bug 难缠得多。</p></div>

### 小结

要解决线程安全问题，先要知道它会以什么形式出现。归纳下来只有三种：可见性、原子性、有序性——也就是常说的**并发三大特性**。它们既是所有线程安全问题的根源，也是后面每一篇的出发点。
